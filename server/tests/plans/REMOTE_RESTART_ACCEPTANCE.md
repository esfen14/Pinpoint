# Issue #182 remote restart acceptance

Opt-in, destructive only to exclusively owned disposable VMs. Never run on a
production host. Owner requested a fresh VM on 2026-10-17.

## Environment and preparation

- Build a separately named appliance from the stock Ubuntu ISO using an isolated
  `VMLAB_CONFIG`, state folder and unused loopback SSH/HTTP ports. Run the VM
  control/endpoint preflight before each mutation. Keep existing lab VMs off.
- Create a separate clean target from the OS-only `base-ready` image. Confirm its
  management endpoint ownership, assign only `10.77.0.2/28` on the isolated lab
  network and keep its NAT management endpoint separate from service SSH.
- Install the pushed issue branch with the installer through `vmlab provision`
  and `vmlab fresh`. Record application/installer SHAs, migrations and health.
- Complete first-run setup through the supported API. Read credentials only from
  private runtime state. Discover only the owned target; verify its live SSH key
  before trusting it. Deploy NCPA through the normal API with the target's
  administrator credentials.
- On the target, install two disposable systemd fixture services: a short service
  whose successful start appends a marker, and a slow service with a 45-second
  start. Keep the allowlist and helpers root-owned; never grant general sudo to
  the deployment account. Use management SSH for fixture preparation, not the
  deployment key.

## Cases and required observations

| Case | Action | Required observation |
|---|---|---|
| RR-01 | Confirm design, installed helper/list ownership and sudoers; run `visudo -c` | Helper root:root 755, list root:root 644, directory root:root 755, sudoers 440 and valid; deployment account has only fixed helper rules |
| RR-02 | Save one fixture service in remote restart settings, clean up/redeploy, enable settings; create remote action with `unit` in Remediation | Settings persist, no credentials in responses; correct action parameters and permission enforcement |
| RR-03 | Stop fixture, deliver a matching HARD failure to the consumer | One successful run and a new target marker; correct pinned device/port/key; output contains only fixed status |
| RR-04 | Repeat within cooldown / hourly cap | No extra marker, one recorded skip per distinct event |
| RR-05 | Set remote restart off, then repeat with device paused, untrusted, and Maintenance Mode | Each distinct event is refused and recorded; no extra marker |
| RR-06 | Change actual target SSH host keys, retaining Pinpoint's old fingerprint; deliver new event | Failed run identifies host-key change, no restart; confirm replacement key only after verifying owned target |
| RR-07 | Remove fixture from device's own root-owned list while leaving it in Pinpoint's list; deliver new event | On-device refusal with exit 3; no extra marker; then restore through normal redeployment |
| RR-08 | Use slow fixture service and deliver a new event | Actual SSH command times out near the command deadline, client closes, one timed_out run; observe any already-submitted systemd job separately |
| RR-09 | Attempt off-list/hostile/extra-argument helper calls and direct systemctl as deployment user | All refused; no fixture marker change and no command execution outside the helper |
| RR-10 | Emit a unique synthetic secret marker in fixture stdout/stderr; inspect run detail, API responses and application logs | Marker, bootstrap password and private key bytes absent; no raw command output exposed |
| RR-11 | Delete a populated action and create another; deliver new event | Old audit rows retain names/outcomes with actionId null; replacement does not inherit old cooldown/hourly count |
| RR-12 | Reopen device settings and edit remote/local unit form in browser | Saved values load correctly, unit control matches type; visible redeploy warning and appropriate loading/error/success behavior |

Events may be delivered directly to the real consumer for isolated runtime cases;
record explicitly whether the trigger was synthetic or generated by real Nagios.
A synthetic HARD event plus real SSH/systemd is evidence for remote execution,
not proof of a Nagios-generated failure chain. Do not mock SSH or systemd in a
case labelled live. Keep raw outputs and private runtime data outside the repo.

## Cleanup

Restore target lists/state after each negative case, stop the slow fixture if it
remains active, and disable/delete test actions. Shut down only the two owned
VMs through verified endpoints. Restore any host virtualization modules that the
owner temporarily unloaded; if sudo is unavailable, ask the owner to restore
them. Retain disks/state unless deletion was explicitly requested. Record every
failure/blocker and safety deviation in a sanitized run report.

## Playwright RR-12 runner

`client/e2e/remote-restart.lab.spec.ts` is the opt-in `issue-182-live` project.
Run only with `PINPOINT_ISSUE182_LIVE=1` after both owned VM endpoint preflights.
Use the no-network Docker/Unix-socket bridge pattern in `scripts/playwright-lab`,
pointing its host socket at the exclusively owned appliance HTTP port (18882
for this run). The container browser uses only loopback 18080 through that socket.
Supply administrator, read-only remediation-reader and target bootstrap credentials
from private runtime state. The reader needs only `remediation.view`; no deployment
or remediation-management permission. Authentication capture stays disabled.

The three browser tests cover settings loading/retry (one explicitly injected
load failure), real save validation and persistence, the visible cleanup warning,
real cleanup and deployment wizard, remote/local unit creation/edit/reload, and
real reader route/API authorization. Created actions remain disabled and are
deleted in teardown. Restore the original service list and disabled switch;
deactivate the reader fixture, shut down owned guests and retain sanitized report
references. Screenshots and Playwright JSON stay in ignored `client/test-results/`.
